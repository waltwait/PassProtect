# 需人工驗證的項目

這些無法自動化，每次動到相關程式碼後都要重跑一次。

## 生體辨識解鎖（規格 §4.4）

1. 以主密碼解鎖，於設定中啟用生體辨識
2. 關閉 app 再開啟 → 應出現生體辨識提示，通過後直接進入，不需輸入主密碼
3. 於提示畫面選「改用主密碼」→ 應可正常回退

## 生體特徵變更後金鑰失效（規格 §4.4）

**破壞性操作，需使用者同意後進行。**

1. 啟用生體辨識解鎖
2. 到系統設定新增一枚指紋
3. 回到 app → 必須要求主密碼，且不可再以生體辨識解鎖

若此項失敗，代表 `setInvalidatedByBiometricEnrollment(true)` 沒有生效，
別人註冊自己的指紋就能打開這個保險庫。這是不可放行的缺陷。

## 生體辨識的邊界情境（規格 §4.4，程式碼註解見 BiometricUnlock.kt）

這三項都是 `BiometricUnlock` 本身完全沒有自動化測試涵蓋的路徑——不是偷懶沒寫，
是需要真的 UI 互動才能觸發。這份文件是唯一的把關。

1. **重新註冊指紋時取消** — 啟用生體辨識解鎖後，到系統設定新增一枚指紋，
   跳出確認畫面時取消。回到 app 應可正常退回主密碼輸入，不可崩潰，
   也不可讓生體辨識卡在一個半設定完成的狀態。
   （這是 `BiometricUnlock.kt` 的 `enroll()` 先清 store 再建金鑰的原因：
   萬一這裡沒處理好，磁碟上會留一個用已刪除金鑰加密的檔案，下次解鎖會在
   使用者按完指紋、以為要成功時才崩潰。）
2. **密文損毀後的自我修復** — 若能構造出一個格式正確但密文本身損毀的
   wrapped-key 檔案（例如透過 root 或備份還原工具修改該檔案幾個位元組），
   下次生體辨識解鎖應該優雅回退主密碼，且**不再重複跳出生體辨識提示**
   （即該檔案已被清除，之後直接要求主密碼）。
3. **提示畫面顯示時關閉 app** — 生體辨識提示彈出後，立刻切到最近工作
   畫面把 app 滑掉（或按返回多次直到 Activity 結束）。系統的生體辨識
   提示 UI 應隨之消失，不可留在畫面上。

## API 29 裝置（規格 §4.4）

本 app 的 `minSdk` 是 29，發布方式是側載給親友，舊裝置的比例不會太低。
`KeystoreKeys.kt` 對 API 29 走的是與 API 30+ 不同的程式碼分支
（`setUserAuthenticationValidityDurationSeconds(-1)`），且改變的是金鑰的
安全語意，不只是相容性寫法——需要在一台真的 API 29 裝置（或該版本的
模擬器）上完整跑一次生體辨識啟用、解鎖、生體特徵變更後失效這三項，
不能只信任 API 30+ 裝置上的測試結果。

## SAF 選檔與授權持久化（規格 §5.2）

1. 首次啟動 → 選擇資料庫位置，指定同步工具監看的資料夾
2. 完全關閉 app 後重開 → 應可直接存取同一個檔，不需重選
3. 到系統設定撤銷該 app 的檔案存取權 → app 應給出明確訊息並請使用者重選
4. 衝突發生時，檢查產生的 `*.conflict-*.kdbx` 檔名——`SafVaultFile` 的
   撞名去重與副檔名保留邏輯只在本機測試過（`DocumentFile.fromFile()`
   包一個一般資料夾），從未對過真正的第三方 SAF provider（Syncthing、
   Nextcloud 等）驗證過。確認衝突檔案的副檔名仍是 `.kdbx`，且沒有被
   provider 自己的去重規則改成看不出來的名字。

## 外部同步衝突（規格 §5.3）

1. 手機與電腦同時開啟同一個資料庫
2. 兩邊各改一筆
3. 讓同步工具把電腦版同步到手機
4. 手機上存檔 → 必須拒絕覆寫，並產生 `*.conflict-*.kdbx`
5. 確認電腦上的改動完好無損

## 螢幕防護（規格 §4.6）

1. 於任一畫面按截圖 → 應被系統拒絕
2. 切到最近工作畫面 → app 預覽圖應為空白，不得顯示提示內容

## 設定畫面：生體辨識啟用/停用

- [ ] 已用主密碼解鎖後，設定畫面開啟「生體辨識解鎖」開關 → 跳出 BiometricPrompt →
      通過後開關維持開啟；殺掉 app 重開、生體辨識解鎖成功
- [ ] 開啟開關後，在驗證畫面按取消 → 開關應維持關閉（enroll 失敗不該假裝成功）
- [ ] 關閉「生體辨識解鎖」開關 → 殺掉 app 重開，應直接進主密碼輸入框，不再跳生體辨識
- [ ] 已啟用生體辨識時變更主密碼 → 殺掉 app 重開、生體辨識解鎖 → 應解出**新**密碼對應的資料庫，
      而不是卡在用舊密碼失敗

## 自動上鎖

- [ ] 解鎖後閒置超過設定的逾時 → app 自動回到解鎖畫面
- [ ] 解鎖後按 Home 鍵切到背景 → 立即上鎖（`AutoLockPolicy.backgroundGraceMillis = 0`）
- [ ] 解鎖後按電源鍵關閉螢幕 → 立即上鎖，不套用任何寬限期
- [ ] 解鎖後持續操作（捲動清單、輸入文字）→ 不會在逾時內被誤判為閒置而上鎖

## 建立新資料庫（規格 §4.7，對真正的第三方 SAF provider）

`UiEndToEndTest` 已經用反射繞過系統資料夾選擇器驗證過這條路徑的邏輯本身，但用的是
`DocumentFile.fromFile()` 包出來的普通目錄，不是真正的 SAF provider——底下這幾項只有
在真正經過系統選擇器、對 Syncthing/Nextcloud 這類第三方 provider 操作時才驗證得到。

- [ ] 選一個第三方同步 provider（非本機儲存）管理的資料夾 → 建立新資料庫 → 確認
      `vault.kdbx` 真的出現在該 provider 的畫面裡（不是只有 app 自己看得到）
- [ ] 在較慢的裝置或刻意調低效能的模擬器上建立新資料庫，觀察是否出現「較慢裝置」提示
      （`KdfParams.exceedsBudget` 判斷為真的情況，目前只在 JVM 測試環境驗證過一定會落在
      最強一級參數，未曾在真的慢裝置上驗證過降級到 `FLOOR` 的路徑）
- [ ] 建立過程中把 app 切到背景又切回 → 不應重複觸發第二次建立，也不應卡住

### 待釐清：`UiEndToEndTest` 建立資料庫等待逾時（2026-08-16 記錄）

同一台裝置（SM-S9210）當天已連續跑過非常多輪 instrumented test，`UiEndToEndTest` 卡在
「等待建立新資料庫完成」這一步，逾時值從 15 秒調到 45 秒、90 秒都還是不夠，最後留寬到
180 秒。用 logcat 交叉確認過：等待期間主執行緒沒有卡住（`AndroidComposeView` 持續在
重繪，只是被同時搶 CPU 的 Argon2 運算拖到只剩 ~2fps），排除了主執行緒同步阻塞、
Activity 生命週期中斷（螢幕休眠/切背景）、崩潰或例外這幾種可能。懷疑是連續高負載
造成裝置過熱降頻，但**尚未在裝置降溫、或只單獨跑這一個測試的乾淨狀態下重新驗證過**，
所以還不能排除是三級 KDF 校準（`KdfParams.calibrate`，DEFAULT→24MiB→FLOOR 依序試）
本身在某些條件下真的需要這麼久。待辦：
- [ ] 裝置降溫後（或用另一台裝置）單獨重跑 `UiEndToEndTest`，記錄實際耗時
- [ ] 若耗時遠低於 180 秒，把逾時值調回合理範圍，避免真的卡住時要等 3 分鐘才報錯
- [ ] 若耗時依然異常長，回頭檢查 `calibrateAndSerialize`/`KdfParams.calibrate` 本身

## 備份還原提示（規格 §4.8）

`VaultHealthCheckTest`/`VaultViewModelTest` 已經涵蓋這條路徑的邏輯本身；下列只有真機才
測得到「使用者真的會看到什麼」。

- [ ] 正常使用一段時間後，用檔案管理員或 provider 端直接刪掉 `vault.kdbx`（保留同步資料夾
      本身）→ 重開 app → 應跳出「偵測到資料庫檔案異常，是否從最近一次的備份還原？」，
      不是被靜默導去「建立新資料庫」畫面
- [ ] 選「還原」→ 應能用還原前的主密碼正常解鎖，且看得到還原前的全部資料
- [ ] 選「不還原」→ 應正常進入建立新資料庫流程，不留下半還原的檔案
- [ ] 把 `vault.kdbx` 的內容改壞（例如用文字編輯器截斷檔案）但保留檔名 → 重開 app →
      同樣應跳出還原提示（檔頭損毀與檔案完全消失，兩種情況走同一個提示）
